# Badge and Attestation Model

## What a Badge Is

A JIVL badge (`jivl-badge.json`, `jivl-badge.svg`, `jivl-badge.md`) is a
compact, derived summary of a single verification report. It is never a
manually-set value — badge generation reads the report's findings and
computes the badge fields from them. See ADR-0005.

## Badge Fields

`schemaVersion`, `skillName`, `skillVersion`, `reportId`, `reportDigest`,
`commitSha` (optional), `result`, `resultLabel`, `verifiedJavaVersions`,
`frameworkEvidence`, `evaluationStatus`, `generatedAt`, `jivlVersion`,
`attestationType`, `expiresAt`.

## Result Values

| Result | Meaning |
|---|---|
| `VERIFIED` | No FAIL or ERROR findings. |
| `VERIFIED_WITH_WARNINGS` | No FAIL or ERROR findings, but at least one WARN. |
| `FAILED` | At least one FAIL or ERROR finding — this **must never** render as Verified. |
| `EVALUATION_PENDING` | Verification itself passed (Verified or Verified with Warnings), but the effectiveness evaluation has not executed. This status describes evaluation state; it is layered onto, not a replacement for, the underlying pass/fail result — a badge must show both. |

## Attestation Types

| Type | MVP status |
|---|---|
| `LOCAL_SELF_VERIFICATION` | **Implemented.** Produced by a local CLI invocation. |
| `CI_SELF_VERIFICATION` | **Implemented.** Produced when JIVL detects a supported CI environment (see `jivl-github-action`). |
| `JIVL_HOSTED_ATTESTATION` | **Not implemented.** Never generated or displayed by this MVP. |

## Non-Negotiable Rules

1. A FAIL or ERROR finding must never produce a `VERIFIED` or
   `VERIFIED_WITH_WARNINGS` badge result.
2. `EVALUATION_PENDING` must be shown whenever no agent baseline/with-skill
   run executed — never silently omitted, never rendered as if effectiveness
   were confirmed.
3. Badge status cannot be supplied manually via CLI flag, config file, or
   API — it is always derived from the report that was actually generated
   in the same invocation.
4. SVG badges are generated locally (no call to an external badge-rendering
   service).
5. `jivl-badge.md` references the SVG by relative path, not a remote URL.
6. The badge/report visibly distinguishes "self-verified through JIVL CLI"
   from "verified through project CI" — these are different trust levels
   and must not be visually conflated.
7. The badge never implies independent, third-party certification. It is
   evidence generated by the tool the skill author themselves ran (or their
   own CI ran), which is valuable but is a fundamentally different trust
   level from an independent hosted attestation service.

## What a Future Hosted Attestation Would Require (Not Built)

If `JIVL_HOSTED_ATTESTATION` is ever built, it would need, at minimum:
project identity verification, commit SHA binding, immutable report
storage, cryptographic signing, expiration, revocation, a defined
re-verification policy, and trusted execution workers independent of the
submitter's own machine/CI. None of this exists yet; see
`docs/enterprise-roadmap.md` for where this fits in a possible future
commercial offering, and `GOVERNANCE.md` for the rule that a favorable
verification outcome can never be purchased, hosted or not.
